Can ML Prioritize Content-Refresh Review Better Than a Simple Rule?

A public-safe research study using the FlyRank ML Internship dataset

Abstract

Question: Can a content-refresh ranking model help prioritize pages for human review better than a transparent rule baseline? Data: The study uses the bundled anonymized FlyRank starter release with 30,000 page-level rows, with metrics aggregated over a trailing 90-day window. Method: A rule baseline is compared with logistic regression, decision tree, and random forest models using a client-holdout split, while label-derived fields and pseudonymous IDs are excluded from model features. Result: The random forest measured Precision@50 of 0.740 versus 0.240 for the rule baseline on the same holdout, with ROC AUC of 0.750 versus 0.627. Use: The output is a directional review queue for human content teams, not an automatic publishing system or a causal claim that refreshing a page will improve performance.

1. Introduction / Problem Statement

Content teams often have more pages to review than they can inspect manually. The practical question in this project is therefore: which existing content items should a human reviewer inspect first for possible refresh work?

The system produces a ranked score, a suggested action, and reason codes. The goal is prioritization support rather than autonomous content editing or publishing.

2. Data

The study uses the bundled anonymized FlyRank starter release containing 30,000 page-level rows. The public artifact does not expose client names, domains, URLs, titles, keywords, or raw search queries.

The supplied page-level metrics are aggregated over a trailing 90-day window. The dataset also contains recent and previous 30-day aggregates used by the reference pipeline.

The public capstone uses the bundled page-level CSV rather than directly querying the larger warehouse. Pseudonymous identifiers are used for grouping or joining but are not used as predictive features.

Label-derived fields such as trend_direction and trend_pct were excluded from model features because they could leak information about the target.

3. Methodology

The target is is_declining_label = 1 when trend_direction == "down". This represents an observed decline in recent impressions relative to the prior 30-day period.

The transparent baseline combines visibility, freshness, position-opportunity, and content-depth signals. The learned models use traffic, content, freshness, CTR, position, engagement, AI-session, and categorical context features.

Validation uses a client-holdout split. Entire pseudonymized clients are held out for testing so that rows from the same client do not appear in both training and test data.

Model selection uses Precision@50 because the practical use case is reviewing a relatively small top-ranked queue. Leakage checks exclude the target, direct target-source fields, and pseudonymous identifiers from predictive features.

5. Limitations & Honest Framing

  • The public result uses the bundled 30,000-row anonymized starter slice, not the full 79-million-row warehouse.
  • The target is an observed impression-decline label, not a measure of whether a refresh would succeed.
  • The model ranks pages; it does not predict Google's ranking algorithm.
  • The client-holdout design improves separation across clients but does not create a causal experiment.
  • Feature importance shows association with model decisions, not proof of cause.
  • A high model score does not mean that refreshing a page will necessarily improve future performance.
  • A production system would require fresh monitoring, data-quality checks, policy review, and revalidation.

Human Review Rules

  1. Open the recommended page.
  2. Check whether the reason code matches the page.
  3. Check current search intent and user needs.
  4. Check whether information is outdated.
  5. Check whether the proposed change is useful.
  6. The human reviewer makes the final decision.

What Should NOT Be Automated

  • Automatically publishing content.
  • Automatically deleting content.
  • Automatically rewriting important facts.
  • Automatically changing medical, legal, financial, or safety information.
  • Automatically sending client-facing recommendations.
  • Treating a model score as proof of causal improvement.

7. Monitoring and Retraining

The recommendation system should be monitored for changes in ranking quality, data distributions, content mix, and feature or label definitions.

  • Review the model if Precision@50 falls materially.
  • Check population or label shift if the declining rate changes materially.
  • Recheck recommendations if the content mix changes.
  • Revalidate the pipeline after feature or label-definition changes.
  • Retrain only when meaningful degradation or data changes justify it.
  • Run fresh holdout validation before accepting a new model.
